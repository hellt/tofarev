The basic operation

An allowed user posts /tofarev review in a PR conversation. GitHub Actions starts the bot workflow.

The prepare job records source revisions. The review job runs OpenCode inside Docker. Token Factory runs the model. The progress job publishes the live session link.

The publish job turns validated findings into one bot comment. The bot does not execute PR code.

You install a small workflow.The bot code stays in hellt/tofarev. Containerlab calls it at a selected commit.
OpenCode starts for each review.The review process uses a fresh working directory. A temporary loopback server supports live session sharing.
The model cannot publish.The review container receives the Token Factory key. Separate jobs receive GitHub App credentials.
01 · Components

Two repositories. Four jobs.

The caller workflow lives in Containerlab. The bot workflow and implementation live in ToFaRev.

A GitHub App supplies the bot identity. GitHub Actions supplies the computers that run the jobs.

The review and progress jobs run in parallel after preparation. Final publication waits for both jobs.

What each component owns

  • Containerlab: the caller workflow, Actions secrets, and App Client ID variable.
  • ToFaRev: the bot workflow, Dockerfile, source code, lockfile, and review policy.

10Manage context and finish within the deadline

The review has a 15-minute deadline. No model-call cap or agent-step cap applies by default.

OpenCode compacts context near its configured 100,000-token window. It preserves a summary and recent conversation.

Compaction uses the same fixed model and high reasoning effort. It consumes time and any explicitly configured call allowance.

The proxy independently caps each HTTP request body at 2,097,152 bytes. This byte cap does not define token capacity.

For the default deadline, finalization starts near 10.5 minutes. The adapter reserves up to 4.5 minutes for final output.

The reserve is the smaller of 4.5 minutes and one-third of the configured duration.

Near that threshold, the proxy removes tool definitions. It asks for supported findings and incomplete-coverage notes.

If trusted configuration sets limits.turns, the adapter also begins finalization near that cap.

For an explicit cap, the agent-step setting uses max(1, limits.turns - 2). Repair still shares the same allowance.

The adapter marks an early finalization partial. It does not turn incomplete analysis into a completed review.

04 · Review data

A source snapshot. Not a PR checkout.

The snapshot gives the agent bounded source context. It keeps Git metadata and executable project setup outside the review process.

Mounted at /source

│   └── ponytail.mdc
├── head/       ← recorded PR head

The snapshot includes eligible files from both revisions. The agent reads relevant files within its budget.

Three revisions serve different purposes

RevisionUse
PR headRead changed code. Link findings to its exact revision.
Target baseRead repository standards from the destination branch.
Merge baseBuild the PR diff. Read old code and link removed lines.

The bot policy comes from the pinned ToFaRev repository. Repository standards supply review criteria, not tool permissions.

The manifest records what the agent can cite

It records head, target base, merge base, changed paths, included files, line counts, notes, and incomplete coverage.

For each finding, validation checks the stated revision and path. The end line cannot exceed the recorded file length.

The manifest does not prove that the model inspected every included file. The agent must describe its coverage.

The standards index identifies separate rule files

The bot reads .cursor/rules/karpathy-guidelines.mdc and .cursor/rules/ponytail.mdc from the recorded target base.

The index records each original path, revision, and snapshot filename. The agent reads the referenced files.

A PR can propose rule changes. Those proposed changes remain review data and cannot replace the current review policy.

Missing rule files cause incomplete coverage. The bot does not invent replacement standards.

The diff shows changes from merge base to head

The diff detects renames and includes five context lines. The bot disables external diff tools and text conversion.

If a diff section exceeds its budget, the manifest records the omission. Source files may still provide relevant context.

The agent can inspect nearby functions, callers, and tests. It must connect each finding to an introduced or worsened issue.

The source trees contain regular UTF-8 files

The CLI reads Git blobs directly. It writes eligible content into separate revision directories.

The snapshot preserves executable-file content as read-only data. It does not execute those files.

Symlinks, submodules, binary files, non-UTF-8 files, and LFS pointers are omitted.

Changed files with lines longer than 2,000 characters cause incomplete coverage. OpenCode's read tool can truncate those lines.

How OpenCode gets installed

  1. The Docker build copies package.json and package-lock.json.
  2. npm ci --ignore-scripts installs the locked dependency set.
  3. opencode-ai@1.18.33 supplies optional binaries for supported platforms.
  4. The Linux x64 build includes opencode-linux-x64@1.18.33.
  5. The adapter calls that platform binary directly.

The direct binary path avoids the npm wrapper's install-script setup. The build keeps development dependencies because OpenCode is listed there.

There is no runtime curl | sh install. OpenCode does not download a newer release during review.

The prepare, progress, and publish jobs also install dependencies. Those jobs do not run OpenCode for inference.

How the agent gets its instructions

  1. The parent reads prompts/containerlab-review.md from trusted bot code.
  2. The parent appends the strict JSON schema and priority definitions.
  3. The parent configures the dedicated tofarev primary agent.
  4. The initial message names source revisions and the changed-path count. It treats the manifest as optional reference data.
  5. The model applies repository standards as review criteria.

The policy checks correctness, clarity, performance, duplication, abstractions, documentation, tests, and topology-schema consistency.

The agent checks schemas/clab.schema.json when the change affects that schema's domain.

The agent must report supported findings. It does not need to fill a finding quota.

What the local proxy permits

  • Only POST /v1/chat/completions.
  • Only model zai-org/GLM-5.3-Flash.
  • Only the fixed Token Factory endpoint.
  • No redirects or provider fallback.
  • A bounded output allowance and request-body size.
  • Trusted reasoning_effort, set to high by default.
  • Up to three retries after transient request failures.

The endpoint is https://api.tokenfactory.nebius.com/v1. The proxy uses its /chat/completions route.

The proxy holds the real API key in the parent process. The OpenCode child receives a minimal environment.

Logs show call counts, request sizes, effort, response-header latency, first-data latency, and total call duration.

Logs do not include request bodies or credentials. The proxy completes a stream at [DONE] without waiting for socket closure.

07 · Isolation

Why use a Docker container?

OpenCode can run directly on a runner. Docker provides an additional boundary around the review process.

The current design separates trusted control code, untrusted PR source, and publication credentials.

Why not run inside the PR checkout?

A PR checkout can contain agent configuration, instruction files, plugins, and executable setup scripts.

An ordinary agent session may discover that configuration. It may also receive shell access and inherited runner credentials.

This design gives OpenCode a fresh working directory. It presents PR files through a separate read-only snapshot.

The bot builds only trusted ToFaRev source. It does not build Containerlab from the PR.

Docker is one layer of this design. Project-configuration controls and tool permissions provide separate layers.

Could direct runner execution work?

Yes. A direct installation can use a fixed OpenCode version and a clean environment.

It would still need a separate working directory, snapshot permissions, configuration controls, process limits, and credential separation.

A normal runner process lacks this container's read-only root filesystem and restricted mount boundary.

Docker also makes local checks closer to production behavior. The same image and flags define the review environment.

The cost includes an image build and dependency installation. The optional progress job adds another runner and trusted CLI build.

Docker does not create a complete outbound firewall.

The parent proxy needs network access to Token Factory. When sharing is enabled, OpenCode also contacts its hosting service.

The container retains ordinary network connectivity.

Mermaid, escaping, and comment-size controls

GitHub supports Mermaid code fences and HTML details blocks in Markdown. The bot uses both formats.

The model can propose a small flowchart or sequence diagram. The fallback publisher validates it before adding a Mermaid fence.

The compact shared-session report does not include Mermaid fences or finding-detail blocks. The viewer shows the structured JSON.

The grammar permits plain nodes, edges, participants, and messages. It excludes links, HTML, styling, and directives.

Diagram input cannot exceed 4,000 characters or 60 non-empty lines. An invalid diagram is omitted.

The report escapes model text as literal text. This prevents model-generated table syntax, arbitrary links, and user mentions.

The default comment limit is 60,000 UTF-8 bytes. The publisher removes whole findings until the report fits.

It removes findings from the end of the sorted list. This drops lower-priority findings first.

Each removed finding loses its row and any fallback details. The report states the omission count.

The report keeps its footer and valid closing markup. It marks the review partial when it omits findings.

10 · Commands and recovery

Understand what starts a review.

Use this local simulator to inspect the caller filter and exact bot check. It does not contact GitHub.

This simulator assumes Containerlab and an open PR. Live admission also checks repository identity and current comment data.

Durable state lives in the bot comment

The bot does not use a separate request database. A hidden, versioned marker stores request state.

OpenCode keeps temporary local session state. Hosted transcripts persist separately when sharing is enabled.

The marker records repository identity, trigger comment, PR number, source SHAs, policy hash, state, and workflow URL.

The marker uses Base64-encoded JSON. Base64 provides encoding, not encryption.

The bot trusts markers only in comments posted by the configured App bot. It validates their fields before reuse.

The request key combines the numeric repository ID with the trigger-comment ID.

Request states

  • Running: the bot has recorded the request and has not finalized it.
  • Completed: the bot has a valid result with complete reported coverage.
  • Partial: the result exists, but coverage or execution has recorded limits.
  • Failed: the bot cannot produce a validated review result.

A stale notice identifies newer PR commits. It does not automatically change a completed report to partial.

No findings means no supported findings within the reported scope. It does not prove that the code has no defects.

Retries, shutdown, and rollback

The GitHub adapter retries network errors, rate limits, and server errors with bounded delays.

If comment creation has an ambiguous failure, the bot searches for its marker before another create attempt.

The inference proxy retries transient network, rate-limit, and server failures. It does not retry authentication through another provider.

A failed review exits nonzero after writing result JSON. A failed final report also makes the publish CLI exit nonzero.

Execution errors appear before snapshot warnings. Skipped requests remain successful no-ops.

A progress-job failure does not discard findings. Final publication waits for progress to finish before updating the report.

Deleting the local session or Actions artifacts does not remove its hosted transcript. The bot does not automatically unshare sessions.

To stop new requests, disable or remove the caller workflow from Containerlab's default branch.

To stop current work, cancel its Actions run. Cancellation can leave a running status comment.

To remove publication access, suspend or uninstall the App. Revoke its private key when needed.

To remove inference access, revoke or replace the Token Factory key.

To roll back code, restore a reviewed SHA in both uses and bot_ref.

Existing reports remain in the PR conversation.
